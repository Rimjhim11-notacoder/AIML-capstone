TAXI FORECASTING REPOSITORY FLOWCHART
=====================================

This map describes the repository as it exists locally. Source code and
configuration define the product; data, models, reports, and databases under
data/, artifacts/, mlruns/, mlflow.db, and predictions.db are generated or
runtime state. .git/, .venv/, and cache folders are environment/tool internals
and are not expanded here.

COMPONENT OUTPUTS, SAVE LOCATIONS, AND ARTIFACT SOURCES
======================================================

Use this section to trace each major product artifact backward to the component
that creates it and the data/model it was created from. Paths are relative to
the repository root unless an S3 or container path is explicitly shown.

1. Source acquisition
  Component: src/data/ingestion.py, invoked by scripts/run_pipeline.py.
  Produces: yellow_tripdata_YYYY-MM.parquet and taxi_zone_lookup.csv.
  Saved at: data/raw/.
  Source: NYC TLC monthly trip-data URL and zone lookup URL in
  config/config.yaml. The source is public TLC data; the configured local
  snapshot is January 2024.
  Command for a fresh download (runs the full pipeline; documented, not the
  command used for the cached local reruns):
  source .venv/bin/activate && python -m scripts.run_pipeline --year 2024 --month 1
  Command actually used with the already-present raw files:
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

2. Cleaning and validation
  Component: src/data/validation.py, called by scripts/run_pipeline.py.
  Produces: trips_clean.parquet and a cleaning report used in the pipeline
  summary.
  Saved at: data/processed/trips_clean.parquet; report fields are saved inside
  data/processed/pipeline_summary.json.
  Source: raw TLC trip Parquet from data/raw/ plus cleaning bounds in
  config/config.yaml.
  Command used (pipeline invokes validation; no separate validation CLI):
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

3. Demand aggregation
  Component: src/data/aggregation.py, called by scripts/run_pipeline.py.
  Produces: pickup_count by pickup zone and hour, including zero-count hours.
  Saved at: data/processed/demand_hourly.parquet.
  Source: cleaned trips in data/processed/trips_clean.parquet.
  Command used (pipeline invokes aggregation; no separate aggregation CLI):
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

4. Feature engineering
  Component: src/features/fare_features.py,
  src/features/demand_features.py, and src/features/calendar.py.
  Produces: fare_features.parquet and demand_features.parquet.
  Saved at: data/features/.
  Source: fare features come from cleaned trip rows; demand features come from
  hourly demand history. Calendar, lag, and rolling settings come from
  config/config.yaml. Demand lag/rolling features use earlier history.
  Command used (pipeline invokes both feature builders):
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

5. Time-based data splitting
  Component: src/data/splits.py, called by scripts/run_pipeline.py.
  Produces: train, validation, and test files for both fare and demand.
  Saved at: data/features/{fare,demand}_{train,val,test}.parquet.
  Source: the matching feature table and split fractions/time columns in
  config/config.yaml. These partitions are chronological, not random.
  Command used (pipeline invokes the split function for each feature table):
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

6. Pipeline summary
  Component: scripts/run_pipeline.py.
  Produces: JSON counts and cleaning summary for the completed pipeline run.
  Saved at: data/processed/pipeline_summary.json.
  Source: cleaning report and row counts from generated demand/fare feature
  tables. It is written after the pipeline stages complete.
  Command used:
  source .venv/bin/activate && python -m scripts.run_pipeline --skip-download

7. Model training and experiment tracking
  Component: scripts/train_models.py -> src/models/train.py,
  src/models/tuning.py, and src/utils/mlflow_utils.py.
  Produces: estimator parameters, validation/test metrics, model files, run
  metadata, and optional registered model versions.
  Saved at: experiment/registry metadata in mlflow.db; run and model artifacts
  in mlruns/. Model names are configured as taxi-demand-forecaster and
  taxi-fare-predictor in config/config.yaml.
  Source: the appropriate train/validation/test Parquet splits in
  data/features/. Tuning/selection uses the configured validation metric
  (RMSE by default); model artifacts are logged from the fitted winner.
  Registration points to the winning MLflow model artifact; `--no-register`
  leaves runs tracked but does not create a registry version.
  Commands actually run:
  source .venv/bin/activate && python -m scripts.train_models --problem fare --n-trials 1 --no-register
  source .venv/bin/activate && python -m scripts.train_models --problem fare --n-trials 2 --no-register
  source .venv/bin/activate && python -m scripts.train_models --problem demand --n-trials 2
  source .venv/bin/activate && python -m scripts.train_models --problem fare --n-trials 1

8. Training-time explanations and model cards
  Component: src/models/shap_utils.py and src/models/model_card.py, called by
  src/models/train.py after selecting the winner.
  Produces: training-stage SHAP summary/bar plots and a model card per problem.
  Saved at: artifacts/fare/ and artifacts/demand/.
  Source: selected fitted model, training features, validation/test metrics,
  feature importance, and project/data metadata.
  Command: generated by the corresponding scripts.train_models invocation
  above; there is no separate training-artifact command.

9. Registered-model responsible analysis
  Component: scripts/responsible/run_analysis.py with src/responsible/
  explain.py, fairness.py, and model_card.py.
  Produces: subgroup RMSE/MAE/MAPE results, global SHAP summary plots, and
  responsible-analysis model cards.
  Saved at: artifacts/responsible/{problem}_fairness.json,
  artifacts/responsible/{problem}_shap_summary.png, and
  docs/model_cards/{problem}.md.
  Source: registered model resolved from MLflow, the matching held-out test
  split in data/features/, and data/raw/taxi_zone_lookup.csv for borough/zone
  labels. SHAP is calculated on a bounded sample; the fairness report uses
  subgroup test results. These outputs describe the selected model/data run.
  Commands actually run:
  source .venv/bin/activate && python -m scripts.responsible.run_analysis --problem fare
  source .venv/bin/activate && python -m scripts.responsible.run_analysis --problem demand

10. Online API predictions
   Component: src/serving/api.py, schemas.py, service.py, registry.py,
   features.py, and predict.py.
   Produces: JSON health, fare/demand predictions, forecasts, and explanations
   returned to the HTTP caller; invalid inputs produce validation responses.
   Saved at: predictions themselves are returned to the caller, not written to
  a local prediction-results file by the API. Structured prediction-capture
  events are emitted to the configured process log stream (stderr by default); hosted infrastructure
   can transport them to S3 through Firehose.
   Source: request JSON, registered MLflow model, serving feature logic, and
   demand history at data/processed/demand_hourly.parquet. Request IDs and
   model reference appear in the response/capture event.
  API startup command actually run:
  source .venv/bin/activate && python -m uvicorn src.serving.api:app --host 127.0.0.1 --port 8000
  Example request commands actually run:
  curl -sS -i -X POST http://127.0.0.1:8000/predict/fare -H 'Content-Type: application/json' -d '{"trip_distance":3.4,"pu_location_id":132,"do_location_id":230,"passenger_count":1,"pickup_datetime":"2024-01-15T18:30:00"}'
  curl -sS -i -X POST http://127.0.0.1:8000/predict/demand -H 'Content-Type: application/json' -d '{"zone":132,"target_hour":"2024-02-01T00:00:00"}'

11. Batch demand forecasting
   Component: src/serving/batch.py, invoked by scripts/batch_forecast.py.
   Produces: recursive predicted_pickups for each selected zone and forecast
   hour; later forecast hours use earlier predictions as history.
   Saved at: rows are appended to the demand_forecasts table in predictions.db
   (path set by serving.batch_db_path in config/config.yaml).
   Source: registered demand model, saved demand history, optional horizon and
   zone arguments. The command prints a small summary to the terminal.
  Command present in the workspace terminal history (completed successfully):
  python -m scripts.batch_forecast --horizon 3

12. Local drift demonstration
   Component: scripts/monitoring/demo_drift_report.py and
   src/monitoring/drift.py.
   Produces: per-feature PSI/KS values and drift flags in JSON.
   Saved at: artifacts/drift/{problem}_drift_metrics.json by default; the
   output directory can be overridden. Dashboard reads this report.
   Source: the problem's training split in data/features/ is the reference;
   the local script samples it for current data and can deliberately shift
   features for a demonstration. A synthetic drift report is not evidence of a
   production incident.
  Example generation command (available, not recorded as run here):
  source .venv/bin/activate && python -m scripts.monitoring.demo_drift_report --problem all --mode drift

13. Managed drift processing
   Component: scripts/monitoring/run_drift_job.py, src/monitoring/capture.py,
   src/monitoring/drift.py, and AWS monitoring configuration.
   Produces: drift_metrics.json, optional Evidently HTML, and CloudWatch summary
   metrics. A no-data run writes a no_data JSON status.
   Saved at: job output directory (default /opt/ml/processing/output), uploaded
   by SageMaker Processing to its configured S3 output; optional metrics go to
   CloudWatch. Captures can be read from local files or an S3 prefix.
   Source: training-split reference features and current API prediction-capture
   records. PSI is the primary flag; KS is supporting distribution context.
  Local dry-run command (available, not recorded as run here):
  source .venv/bin/activate && python -m scripts.monitoring.run_drift_job --problem fare --current-dir ./captured --output-dir ./out --no-cloudwatch

14. Dashboard
   Component: dashboard/app.py, api_client.py, data.py, and sections.py.
   Produces: rendered dashboard pages with live API results and stored evidence.
   Saved at: no dashboard report is written by normal viewing; the app reads
   reports from artifacts/responsible/, artifacts/drift/, docs/model_cards/,
   and zone labels from data/raw/taxi_zone_lookup.csv.
   Source: HTTP API responses plus local static artifact files. API and report
   timestamps/model references may differ.
  Local launch command (documented; dashboard was not launched here):
  source .venv/bin/activate && API_BASE_URL=http://127.0.0.1:8000 python -m streamlit run dashboard/app.py --server.address 127.0.0.1 --server.port 8501

15. Tests and CI
   Component: tests/, pyproject.toml, scripts/ci_local.ps1, and buildspec.yml.
   Produces: pass/fail output in the terminal or CI logs. The configured
   CodeBuild coverage command additionally creates coverage.xml.
   Saved at: coverage.xml in the CodeBuild workspace/artifact output when the
   coverage buildspec runs; ordinary local pytest results are terminal output.
   Source: test fixtures/synthetic data and the code under src/. Tests do not
   require the production TLC files or AWS.
  Local test command actually run:
  source .venv/bin/activate && python -m pytest
  CI coverage command defined in buildspec.yml (not run in CodeBuild here):
  pytest --cov=src --cov-report=term-missing --cov-report=xml

16. Container image and cloud deployment
   Component: docker/Dockerfile, docker/docker-compose.yml, buildspecs,
   scripts/aws/, and infra/terraform/.
   Produces: API/dashboard container images, optional ECR image tags, and (when
   explicitly deployed) AWS resources/service rollout.
   Saved at: locally in the Docker image store, then in ECR for cloud delivery;
   Terraform-managed state/resources are outside the source tree. The API image
   includes code, dependencies, portable MLflow registry/artifacts, and demand
   history. Compose development mounts can override these files.
   Source: repository code/configuration, prepared MLflow registry and mlruns,
   Parquet demand history, dashboard evidence, AWS parameters/credentials, and
   successful quality gates. The repository configuration alone is not proof
   that an image or AWS service was built/deployed.
  Docker command documented for an available Docker installation (not run;
  Docker CLI was unavailable):
  docker compose -f docker/docker-compose.yml up --build

17. Gated retraining
   Component: retraining/pipeline.py, train_step.py, scripts/monitoring/
   evaluate_models.py, and build_and_deploy.py.
   Produces: candidate MLflow registry, training_summary.json,
   evaluation.json, and—only if release conditions and deploy authorization
   pass—a CodeBuild request for publishing/deployment.
   Saved at: SageMaker Processing output directories and their configured S3
   outputs; gated registry database and mlruns are uploaded to the deployment
   artifact bucket. Evaluation JSON is read by the pipeline quality gate.
   Source: prepared feature splits, seed/baseline MLflow registry, tuning
   settings, RMSE thresholds, and explicit deployment authorization. Drift
   alarms do not automatically retrain or deploy models.
  Command used: none. The AWS/SageMaker retraining pipeline was inspected but
  not submitted; execution requires configured AWS credentials, roles, images,
  S3 inputs, and explicit deployment authorization.

Artifact lineage summary:
NYC TLC -> raw Parquet/CSV -> cleaned trips + hourly counts -> feature tables
and chronological splits -> MLflow runs/models -> SHAP/fairness/model cards
and API inference -> batch/database or monitoring reports -> dashboard/review.
Each arrow is a data dependency; it does not imply every stage runs
automatically.

OVERALL ROLE
============

The repository moves from raw TLC data to clean feature tables, trained and
registered models, online/batch predictions, responsible-AI and monitoring
evidence, and optional delivery or retraining. Tests and documentation support
each stage. Dashboard, monitoring, explainability, and serving are connected
support functions; the lifecycle is not a single automatic pipeline from alarm
to deployment.
